# LlamaGLM status

The active implementation on `master` is the repaired v0.8.0 upstream-RPC prototype exported from the VM (engine snapshot `502ff59`, launcher snapshot `6664b7d`). The engine now lives at the repository root; launchers are in `scripts/`. The original custom stage-runtime branch remains separate.

Both Claude and Codex are authorized to develop, commit, and push directly to `master`. Fetch the latest remote changes before starting, preserve the other developer's commits, and update this handoff with changes, test results, open issues, and next steps. Force pushes remain prohibited.

RPC intentionally uses the upstream unauthenticated protocol. The accepted prototype configuration uses 8K context and the documented RAM/mmap placement. See [FIRST-RUN.md](FIRST-RUN.md) and [LIMITATIONS.md](LIMITATIONS.md).

The import review fixed a CUDA self-test that could pass without executing CUDA tests, worker-reserve integer overflow and invalid settings, the packaging script's nested-repository assumption, and an overly broad Clang-only shim dependency. Launcher regression checks and actual local RPC tests passed on CPU. [Review and validation](docs/REVIEW-v0.8.0.md) distinguishes these checks from the original VM reports.

Native Windows CPU and SM89/SM120 compilation is defined in `.github/workflows/llamaglm-rpc-windows.yml`. GitHub-hosted runners exercise CPU fixtures; CUDA execution, full-model inference, and operation on the three PCs still need hardware validation. Its CUDA jobs currently fail before any test runs: the static test executables import `nvcuda.dll`, which hosted runners lack (the stage-runtime branch delay-loads it in `ggml/src/ggml-cuda/CMakeLists.txt`).

v0.8.1 package: `.github/workflows/llamaglm-package-windows.yml` (manual `workflow_dispatch`) builds the user's Windows package from this source with MSVC + nvcc (CUDA 12.8.1, sm_89 + sm_120a, AVX2 CPU backend, shared libraries with dynamically loaded backends, app-local MSVC runtime) and uploads it as the run's artifact. It checks that every imported DLL is in the package or part of Windows, then runs `--version`, the RPC reserve regression, Gate 1 against two local CPU workers and the launcher tests on the runner. It replaces the VM's clang cross build (DECISIONS D10); source, CUDA version, GPU targets and launchers match v0.8.0 plus the import-review fixes. `start-stage-a.ps1` now accepts `llama.dll` (MSVC name) as well as `libllama.dll`, which also fixes `-BinDir` with the official llama.cpp build.

First package run: [40113550550](https://github.com/Protonburn35/LlamaGLM/actions/runs/40113550550) at `bb0bc7d`, 44 min, all checks passed (Gate 1 48/48 comparisons, 8 reserve cases, launcher tests under PowerShell 5.1). Artifact `LlamaGLM-v0.8.1-win-cuda-cu12.8-sm89-sm120-x64`, 615,204,138-byte zip, SHA-256 `8284c22c9b7e763afb137c5c752e4d752de598d2b015cd8d0ba4d97f509876a1`, expires 2026-11-23. Every one of the 145 CUDA modules in `ggml-cuda.dll` has compressed SASS for sm_89 and sm_120 (no PTX); the v0.8.0 clang build had the same coverage uncompressed (141 modules, 304 MiB), hence 52 MB vs 336 MB. Not run on a GPU or on the PCs yet.
